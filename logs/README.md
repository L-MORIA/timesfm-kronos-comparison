# Логи прогонов

## ⚠️ Единицы измерения изменились 2026-10-14

Записи **до 2026-10-14** и записи **после неё несопоставимы**.

| | до 2026-10-14 | с 2026-10-14 |
|---|---|---|
| Бары MOEX | часовые (`interval=60`), ~15 свечей/день | дневные (`interval=24`), 1 свеча = 1 торговый день |
| Что значил `horizon=30` | 30 **шагов** ≈ **2 календарных дня** | 30 **баров** = **30 дней** |
| Горизонты Kronos | все три = один и тот же прогон на 500 шагов | разные: 30 / 60 / 90 баров |
| Порог сигнала | ±2% от цены | ±1σ h-шаговой диффузии |
| Воспроизводимость | нет (один случайный сэмпл) | да (seed + усреднение 8 сэмплов) |
| Wall-clock | ~10–15 мин | ~90–120 с |

### Как отличить записи

Новые прогоны пишут в лог две служебные строки:

```
units: daily bars (interval=24), horizons=[30, 60, 90] days, seeds=20261014
signal mode: z_vol (порог ±1σ)
```

Если этих строк нет — запись сделана в старых часовых единицах.
Ищите их в начале каждой секции внутри `comparison_*.log` (файл дописывается,
секций за день может быть несколько).

### Старые файлы

`comparison_*.log` до 2026-10-14 (77 файлов, июнь–октябрь) оставлены как есть:
каталог игнорируется git, перенос мог бы привести к потере данных. Удалять
или не использовать — на ваше усмотрение; **как источник сигналов они не
пригодны**.

## Состав файлов

| Файл | Что |
|---|---|
| `comparison_YYYYMMDD.log` | **отчёт прогона**, дописывается; формат закреплён разделом ниже |
| `run_YYYYMMDD_HHMMSS.log` | **технический лог прогона** (logging): полный формат с timestamp, уровнем и трейсбеком |
| `run_YYYYMMDD_HHMMSS.txt` | вывод bash-обёртки `run_with_sig.sh` — **не используется с 2026-09-24** |
| `last_run.log` | копия одного из ранних прогонов |
| `verify_*.txt`, `exp_*.txt` | результаты проверок и экспериментов |
| `backtest_*.txt` | журналы walk-forward бэктеста |

### Отчёт против технического лога

С 2026-10-15 в скрипте два разных файла, и путать их нельзя:

| | `comparison_*.log` | `run_*.log` |
|---|---|---|
| что внутри | таблицы, интерпретация, диагностика | весь ход прогона: фетч, модели, ошибки, DEBUG, трейсбек |
| формат | **менять нельзя** — по строкам `units:`/`signal mode:` отличают юниты | свободный, перезаписывается каждый запуск |
| кто читает | сверка прогонов, `logs/README.md` ниже | разбор после падения |

Cron-задача в чат доставляет **stdout** (обёртка читает `proc.stdout` и печатает
его дословно). Поэтому stdout-хендл настроен на `sys.stdout` с форматом
`%(message)s`, без timestamp и уровней, — сообщения в чате выглядят как раньше.
Полный формат с уровнями уходит только в `run_*.log`.

`comparison_*.log` продолжает дописываться тем же текстом, что и до этого:
его формат — это механизм различения старых и новых юнитов.

Cron задачи `TimesFM+Kronos MOEX Comparison` сам этот каталог не пишет —
он зовёт проектный скрипт напрямую через обёртку hermes, а скрипт уже
дописывает `comparison_YYYYMMDD.log`.

## Кодировка артефактов (`*.txt`) — урок 2026-10-16

`python script.py > file` в PowerShell даёт кракозябры (`╨и╨Р╨У`): PS читает
UTF-8-вывод python по кодовой странице консоли (CP866) и переписывает
в файл уже искажённым. Так были повреждены 18 логов за 15–16.10.

**Правильный запуск вывода в файл:**

```powershell
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
python experiments\panel_daily.py ... > logs\panel_full.txt
```

**Восстановление уже повреждённого файла** (двойное кодирование обратимо:
utf-8 → cp866-трактовка → utf-8; это ровно цепочка возникновения):

```python
raw = open(p, 'rb').read()
fixed = raw.decode('utf-8').encode('cp866').decode('utf-8')
open(p, 'w', encoding='utf-8', newline='').write(fixed)
```

Маркер поражения — блочные знаки U+25xx (`E2 95` в байтах). Оригиналы
исправленных файлов сохранены в `_mojibake_backup_20261016/`.
